# Edge cases — rules INVTRA follows

Each rule below is implemented in code (file references in brackets) and most are
covered by `tests/flow.test.ts`.

| Situation | Rule |
| --- | --- |
| **Invalid phone number** | Every number is normalised to E.164 with libphonenumber when it is added or imported; numbers that can't be valid are rejected with a clear message (import preview marks the row, it is not imported). National numbers use the event's country (from its time zone) unless the customer picks another. If WhatsApp itself rejects the number (error 100 / 131030 …) the guest is marked **Failed — invalid number**. [`src/lib/phone.ts`, `src/server/guests/service.ts`, `src/server/queue/handlers.ts`] |
| **Guest doesn't have WhatsApp** | The Cloud API accepts the message, then reports `failed` with code **131026** via webhook. The guest becomes **Failed — doesn't seem to use WhatsApp**; the dashboard suggests checking the number. Editing the number resets the guest so it can be resent. [`src/server/whatsapp/webhook.ts`, `src/server/guests/service.ts#editGuest`] |
| **WhatsApp message fails** | Transient errors (rate limits 130429/131056, 5xx, network) are retried by the queue with exponential backoff (15s → 30 min, 6 attempts). Permanent per-recipient errors fail that guest only. *Systemic* errors (template paused/disabled, bad token…) cancel the rest of the batch so hundreds of messages don't fail one by one, and are logged in **Admin → System errors**. [`src/server/whatsapp/errors.ts`, `src/server/queue/*`] |
| **Guest presses Accept twice** | The answer is idempotent (no second RSVP record). Pressing Accept again re-sends the invitation at most once per 10 minutes, and never within 2 minutes of the previous delivery — handy when a guest lost the message, harmless on double taps. [`src/server/rsvp.ts`, `webhook.ts`, `handlers.ts#deliverInvitation`] |
| **Guest presses Decline after accepting** | Allowed until replies close. The guest becomes **Declined**, attendance is set to 0, the change is logged in the RSVP history and activity feed, the invitation page shows the declined state and hides the entry QR, and door check-in shows a warning if the old QR is scanned. Accepting again later re-issues the invitation. |
| **Guest declines** | Status **Declined**; only a short thank-you is sent (inside the 24-hour window). The invitation image, QR and link are **never** sent. |
| **Customer edits the event after sending** | Anything printed on the invitation (names, date/time, venue, address, theme, design, language, custom image) bumps the event's `contentVersion`. Images are re-rendered on demand for the new version. The dashboard shows "N guests have the previous version — send update", which sends the regenerated image to accepted guests: as an interactive message inside the 24-hour window, otherwise with the approved **invitation update** template. Guests who haven't answered automatically get the latest version when they accept. [`src/server/events/service.ts`, `src/server/sending/service.ts#sendUpdateToAccepted`] |
| **Customer changes the design** | Same as above — design changes are versioned; the editor warns when accepted guests hold an older version. |
| **QR scanned multiple times** | Every scan is recorded (time, guest, invitation, whether the host scanned it). Repeat triggers within 10 seconds (camera apps opening the URL twice) are ignored. Dashboard shows first scan and total scans. [`src/server/invitations/public.ts#recordScan`] |
| **Invitation link opened before acceptance** | The page shows the full invitation and an RSVP prompt (if web RSVP is enabled); the entry QR is locked until the guest accepts. |
| **Customer deletes an event** | Soft delete: invitation links and QR codes stop working immediately ("no longer available", nothing about the event is revealed), queued messages are cancelled, Accept/Decline presses get a polite "no longer active" reply. All data and files are permanently purged after 30 days. [`src/server/events/service.ts#deleteEvent`, `src/server/maintenance.ts`] |
| **Admin deactivates an event or account** | Same effect as deletion for guests, but reversible by staff. Deactivated accounts can't sign in and their sessions are revoked. |
| **Customer resends an invitation** | Guests who haven't answered (or whose delivery failed) get the Accept/Decline message again (10-minute cooldown per guest); accepted guests get their invitation image again; declined guests are skipped — the host can change an answer manually. |
| **Duplicate phone numbers** | One guest per number per event (database constraint). Imports report duplicates within the file and against the existing list, and skip them. |
| **Guest forwards their invitation link** | The link is a bearer link — anyone with it can view that one invitation, which is why the page is personal ("This invitation is for Khalid · Admits 2") and shows nothing about other guests. The QR is tied to that guest: at the door the host sees the guest's name, party size and RSVP status, so a forwarded pass is easy to spot, and over-capacity check-ins are flagged. A Decline/Accept button can only be pressed from the guest's own WhatsApp number (webhook verifies the sender). |
| **Same number invited to several events** | Button payloads carry the invitation token, so replies are always routed to the right event, never guessed by phone number. |
| **RSVP deadline / event over** | Answers after the deadline (end of that day in the event's time zone) or after the event are refused with a polite message. |
| **Webhook delivered twice / out of order** | Inbound messages and statuses are de-duplicated by WhatsApp message id; delivery statuses only move forward (sent → delivered → read). |
| **Spoofed webhooks** | Requests without a valid `X-Hub-Signature-256` HMAC are rejected (401) before parsing. |
| **Guest messages outside the 24-hour window** | Free-form messages are only sent within 24 h of the guest's last message; otherwise INVTRA uses an approved template, or (for courtesy messages) sends nothing. |
